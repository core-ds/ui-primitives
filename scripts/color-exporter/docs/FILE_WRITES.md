# Запись JSON и восстановление при ошибке

`json-files.mts` читает JSON и проверяет пути. `file-transaction.mts` отвечает за запись уже рассчитанных текстов. В нём нет правил палитр, Figma или GitHub.

## Последовательность

1. Конвейер рассчитывает все активные палитры. Ошибка любой страницы запрещает запись всех результатов.
2. Проверяются пути внутри репозитория: промежуточные узлы должны быть папками, конечный — обычным файлом либо отсутствовать. Символические ссылки не допускаются. При чтении конечный путь дополнительно открывается без перехода по ссылке.
3. Перед записью сверяются исходные тексты и права. Новый JSON должен по-прежнему отсутствовать.
4. Рядом с целями создаются уникальные временные файлы: новый текст и, для существующего JSON, исходная копия. Все параллельные записи дожидаются завершения, включая неуспешные. До их общего успеха цели не меняются.
5. Непосредственно перед каждой заменой исходное состояние проверяется ещё раз. Существующий JSON заменяется через `rename`; новый создаётся через `link`, который не перезапишет появившийся путь. Права существующего файла сохраняются, нового — `0644`.
6. После успеха временные файлы удаляются. Ошибка очистки сообщается, а не скрывается.

## Если одна из замен не удалась

Уже установленные файлы обрабатываются в обратном порядке. Перед восстановлением проверяются номер файла, устройство, текст и права: целевой путь должен всё ещё содержать установленную нами версию.

- Существующий JSON восстанавливается из подготовленной исходной копии.
- Новый JSON удаляется, только если в нём осталась наша версия.
- Чужое изменение не заменяется исходной копией и не удаляется. Запуск завершается ошибкой.
- Если восстановить существующий файл не удалось, полная исходная копия остаётся в `*.color-exporter-<идентификатор>.rollback.tmp`. Сообщение об ошибке содержит её точный путь.

Неудача восстановления одного файла не отменяет попытки восстановить остальные. Все ошибки сохраняются вместе.

## Границы гарантии

Атомарна замена **одного** файла, а не всей группы. Восстановление выполняется при ошибках, которые процесс смог перехватить. Отключение питания, принудительное завершение процесса и изменение файлов другим процессом между последней проверкой и заменой не покрываются общей транзакцией.

Поэтому запускать запись нужно в отдельной рабочей папке без параллельных изменений. GitHub Actions предоставляет отдельную рабочую папку задания, а очередь запусков предотвращает одновременную синхронизацию служебной ветки. Для локального предварительного просмотра есть `--check`, который вообще не записывает файлы.

После неудачного восстановления сначала сохраните нужную текущую версию и указанную исходную копию, затем сравните их. Резервные файлы нельзя массово удалять, пока восстановление не завершено. Сбой до успешной записи не приводит к публикации: экспортный коммит и отправка выполняются только после успешного завершения конвейера. Подготовка служебной ветки выполняется раньше и не является публикацией результата.

Если процесс принудительно остановили между двумя заменами, рабочая папка может содержать неполный результат. Это техническое ограничение записи нескольких файлов, а не дополнительное решение или настройка со стороны дизайнера. На сервере используется отдельная рабочая папка задания; следующий запуск начинает проверку заново. Локально для просмотра результата используйте `--check`, а для испытания записи — отдельную копию репозитория. Автоматическое восстановление после отключения питания здесь не заявляется.

## Проверки

`tests/file-transaction.test.mts` создаёт настоящие временные файлы. Подмена отдельных операций воспроизводит сбой подготовки, задержанную соседнюю запись, сбой второй установки, ошибку восстановления, чужую правку и отказ очистки. `tests/json-files.test.mts` проверяет права, чтение и ссылки в пути. Тесты не трогают JSON рабочего репозитория.
