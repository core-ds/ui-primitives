# Работа GitHub Actions

## Когда процесс разрешён

Процесс запускается только вручную через `workflow_dispatch`. Задание и сам код независимо проверяют:

- репозиторий равен `core-ds/ui-primitives`;
- выбранная ветка является основной веткой репозитория;
- `context.sha` содержит полный SHA коммита.

Одновременно разрешён один экспорт на репозиторий. Следующий ручной запуск ждёт текущий. Максимальное время — 15 минут.

## Разрешения и секреты

Нужны только:

- `contents: write` — создать коммит и отправить служебную ветку;
- `pull-requests: write` — прочитать, создать или обновить реквест.

`FIGMA_TOKEN` передаётся через хранилище секретов GitHub. Открытый ключ единственного Color Exporter хранится в `core/figma-source.mts`; модули палитр не могут выбрать другой файл.

## Этапы процесса

1. Получить полную историю Git через `fetch-depth: 0`.
2. Подготовить Node.js 24.
3. Выполнить `npm ci` по закреплённому `package-lock.json`.
4. Собрать весь каталог `scripts` командой `npm run build`.
5. Запустить собранные проверки экспортёра из `dist/color-exporter/tests/*.test.mjs`.
6. Проверить только рабочий код экшена с минимальным покрытием: 100% строк, 95% ветвей, 98% функций. Сами тестовые файлы в процент не входят.
7. Только после этого запустить собранный `dist/color-exporter/src/action/run-github-action.mjs`.

Все внешние GitHub Actions закреплены полными SHA. Кеш пакетов отключён, чтобы процесс не зависел от неочевидного внешнего состояния.

Внутри экшена сначала обнаруживаются явные модули особых палитр. Затем один раз загружается полный REST-ответ Color Exporter `JGR9GpDXUneyYHfDdb7BDT`. Список активных наборов определяется по страницам `colors_<название_набора>.json`: явный модуль имеет приоритет, а для новой стандартной страницы правила создаются в памяти. Репозиторий `styles` не используется как реестр наборов, списка исключений нет.

После разбора экшен отдельно пишет в журнал стабильный список настроенных особых страниц, которых нет в ответе Figma. Тот же список возвращается в поле `inactiveConfiguredPages` результата запуска. Поэтому пропуск явного модуля виден даже тогда, когда для его JSON не было ожидающей разницы и согласовывать нечего.

## Подготовка служебной ветки

Постоянное имя — `feat/update-colors`.

1. `git ls-remote --exit-code` проверяет точную удалённую ссылку.
2. Код `2` означает отсутствие ветки. Новая локальная ветка создаётся от точного `context.sha`.
3. Код `0` означает существующую ветку. Она загружается, выбирается локально и объединяется с `context.sha` обычным `merge`. Если локальная вершина после объединения отличается от загруженной удалённой, ветку нужно отправить даже без новых изменений JSON.
4. Любой другой код считается ошибкой сети или доступа.

История не переписывается. Конфликт объединения останавливает процесс и требует ручного решения.

## Зачем отдельно читать JSON основной ветки

Служебная ветка может уже содержать результат прошлого запуска. Например, `push` прошёл, а создание реквеста через GitHub API завершилось ошибкой.

Поэтому у каждого файла есть две исходные версии:

- текущий текст служебной ветки нужен, чтобы решить, требуется ли физическая запись;
- текст из `context.sha` нужен, чтобы честно вычислить разницу реквеста и его описание.

Сначала `git ls-tree -z` проверяет наличие точного пути и обычный файловый тип в указанном SHA. Символическая ссылка, каталог или другой тип запрещены. Существующий JSON читается командой `git show <context.sha>:<targetJson>`, а отсутствие пути означает новый набор с логической исходной версией `{}`. Благодаря этому повторный запуск снова видит новые, изменённые и устаревшие токены относительно основной ветки, даже если служебная ветка уже готова.

Исходная версия читается лениво: только после того, как одноимённая страница действительно найдена. JSON без страницы не читается и не проверяется.

## Согласование служебной ветки с текущими страницами

После синхронизации экшен ищет цветовые JSON, которые отличаются в постоянной служебной ветке от `context.sha`, но отсутствуют среди текущих активных страниц. Такая разница могла остаться только от предыдущего запуска, когда страница ещё существовала.

- Если путь существует в основной ветке, рабочая копия и индекс восстанавливаются из `context.sha`.
- Если путь появился только в служебной ветке, `git rm` удаляет его и сразу подготавливает удаление в индексе. Повторно передавать этот отсутствующий путь в `git add` не требуется.
- Если разницы нет, опубликованный JSON остаётся нетронутым.

Это убирает незавершённое изменение исчезнувшего набора, но не удаляет опубликованный JSON из основной ветки и не отменяет только что рассчитанные изменения активных страниц. На новой чистой служебной ветке шаг ничего не меняет.

## Проверки перед публикацией

После синхронизации выполняются:

1. Подготовка индекса:
   - `git add -A --` получает только `targetJson` активных страниц;
   - изменения исчезнувших страниц уже подготовлены восстановлением или удалением;
   - `git diff --cached --check` ищет ошибки пробелов;
   - `git diff --cached --name-only --no-renames -z` запрещает неожиданный путь, в том числе когда список активных страниц пуст.
2. Проверка итогового дерева:
   - `git diff --cached --raw --no-abbrev --no-renames -z <context.sha> --` сравнивает именно индекс с точным SHA основной ветки;
   - каждый оставшийся изменённый путь обязан входить в список активных страниц;
   - активный JSON нельзя удалить, заменить ссылкой или другим типом, изменить его права;
   - новый JSON обязан иметь обычный режим `100644`, а существующий сохраняет режим основной ветки;
   - `git ls-files --stage -z` дополнительно проверяет наличие обычных файлов всех активных страниц и отсутствие конфликтов индекса.
3. Проверка плана публикации:
   - список JSON с `changed: true` обязан точно совпасть с разницей индекса: проверяется каждый результат;
   - допускается не более одного открытого реквеста с правильным положительным номером;
   - проверка отчёта и построение полного описания заканчиваются до коммита и отправки.
4. Проверка отправляемого коммита:
   - `git write-tree` фиксирует точное проверенное дерево индекса до обращения к GitHub;
   - перед `push` дерево `HEAD` сравнивается с зафиксированным: изменение индекса хуком коммита останавливает отправку.

Имена из Git разделяются нулевым байтом и сравниваются без удаления пробелов или другого преобразования. Поэтому `styles/colors_example.json ` с конечным пробелом не превращается в разрешённый `styles/colors_example.json`.

Перед второй проверкой неактивные пути вида `styles/colors_*.json` уже возвращены к основной ветке. Проверка ловит оставшийся посторонний файл из старого коммита ветки, даже если незаписанное изменение рабочей копии скрывает его. Неотслеживаемые посторонние файлы не добавляются в индекс и не отправляются.

## Пять возможных результатов

### 1. Разницы с основной веткой нет

Если индекс пуст и объединение с основной веткой не продвинуло локальную вершину, коммит и `push` не выполняются. Список реквестов всё равно читается. Новую вершину после объединения нужно отправить обычным `push`, даже когда дерево уже совпадает с основной веткой.

Если открытый реквест уже существует, результат получает `stalePullRequest: true` — «реквест устарел». В журнале появляется его номер и просьба проверить и закрыть реквест вручную. Процесс не закрывает его и не удаляет ветку автоматически.

### 2. Есть новый индекс и разница с основной веткой

Создаётся коммит, выполняется обычный `push`, затем создаётся или обновляется реквест.

### 3. Индекс пуст, но ветка уже отличается от основной

Это штатное восстановление после прошлого успешного `push`. Новый коммит цветов не нужен. Если объединение с новой основой создало новую локальную вершину, выполняется обычный `push`; иначе повторная отправка не требуется. Процесс создаёт отсутствующий реквест или обновляет существующий.

### 4. Ветка отличается, но синхронизатор не подтверждает разницу Figma

Процесс останавливается до коммита и отправки. Сверяются списки путей целиком, поэтому настоящее изменение одной палитры не разрешает необъяснённую разницу соседней. Изменения типов и прав отдельно блокируются проверкой Git ещё до чтения списка реквестов.

### 5. Исчезнувшая страница убрала последнюю разницу

Согласование добавляется в индекс, коммитится и отправляется обычным `push`. После этого дерево служебной ветки совпадает с основной, поэтому новый реквест не создаётся и существующий не обновляется. Для старого открытого реквеста возвращается `stalePullRequest: true`, его номер виден в журнале; закрытие остаётся ручным действием.

## Создание или обновление реквеста

Разрешён ноль или один открытый реквест из `feat/update-colors` в основную ветку. Два означают неоднозначное состояние и останавливают процесс до коммита и `push`.

Описание строится только из проверенного структурированного результата. Оно содержит:

- таблицу всех активных JSON с результатом проверки каждого;
- числа активных и устаревших токенов;
- число секций, фреймов и прямоугольников;
- виды изменений;
- полный список ключей, впервые получивших `deprecated: true`;
- гарантии детерминированности и отсутствия автоматического слияния.

Если реквеста нет, вызывается создание. Если один есть, меняются только заголовок и описание. Код не выполняет слияние, одобрение или закрытие.

## Почему используется обычный `push`

Существующая ветка продолжается, а не переписывается. Если человек или другой процесс изменил её после чтения, обычный `push` будет отклонён. Чужая история не потеряется.

## Что остаётся после ошибки

- Ошибка сборки или проверки: Figma ещё не читалась.
- Ошибка Figma или раскладки: ни один JSON не записывается.
- Ошибка одной палитры: остальные тоже не записываются.
- Оставшийся после согласования посторонний путь: коммит, `push` и GitHub API не вызываются.
- Два открытых реквеста: коммит и `push` не выполняются.
- Неправильный номер реквеста или расхождение отчёта с индексом: коммит и `push` не выполняются.
- Хук коммита изменил проверенное дерево: локальный коммит остаётся, но `push` не выполняется.
- Ошибка `push`: удалённая история не переписывается.
- Ошибка создания реквеста после успешного `push`: ветка остаётся; следующий запуск восстанавливает реквест без нового коммита.
- Пустая итоговая разница при старом открытом реквесте: реквест не создаётся и не обновляется, возвращается `stalePullRequest: true`, в журнале виден номер для ручной проверки. Согласующий коммит или объединение с новой основой при необходимости отправляются в служебную ветку.

## Чего процесс не делает

- не использует ИИ и Figma MCP;
- не меняет Figma;
- не читает API переменных Figma;
- не применяет принудительную отправку Git;
- не удаляет опубликованные JSON из основной ветки из-за отсутствия страницы;
- не закрывает реквесты;
- не выполняет автоматическое слияние;
- не выводит секрет в адрес, ошибку, тестовый слепок или описание.
