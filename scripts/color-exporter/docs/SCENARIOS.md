# Сценарии работы экшена

Этот документ описывает поведение будущего экшена от запуска до реквеста. Он не описывает создание раскладок в Figma: к моменту запуска страница и узлы уже существуют.

## Общая последовательность одного запуска

1. Экшен проверяет репозиторий, основную ветку, полный SHA, наличие секрета и доступность Git/GitHub-клиента.
2. Находит явные модули особых палитр. Они задают правила страниц, но не источник Figma.
3. Настраивает автора Git и открывает постоянную служебную ветку `feat/update-colors`.
4. Если ветки ещё нет, создаёт её от точного SHA основной ветки. Если есть — получает её и обычным `merge` подводит к текущей основной ветке.
5. Один раз получает полный ответ Figma REST для постоянного Color Exporter `JGR9GpDXUneyYHfDdb7BDT`.
6. Находит все страницы, чьи имена подходят `colors_<название_набора>.json`.
7. Для страницы с явным модулем использует модуль. Для остальных создаёт стандартные правила в памяти.
8. Сортирует активные наборы по целевому пути, чтобы результат не зависел от порядка страниц и операционной системы.
9. Только для найденных страниц лениво читает исходный JSON из точного SHA основной ветки.
10. Разбирает и проверяет все страницы. Пока не успешны все активные наборы, запись не начинается.
11. Для каждого набора строит итоговый JSON относительно основной ветки и при необходимости записывает его в рабочую копию.
12. Согласует остаток служебной ветки от прошлых запусков: убирает ожидающие изменения JSON страниц, которых теперь нет.
13. Добавляет в индекс только JSON активных страниц и пути, согласованные на предыдущем шаге.
14. Проверяет итоговый индекс: точные пути, типы и права файлов, всю разницу с основной веткой.
15. Проверяет соответствие этой разницы результату каждого набора, открытые реквесты и их номера. Допускается не больше одного реквеста. Заранее готовит его описание.
16. При наличии изменений создаёт коммит. Перед обычным `push` сверяет коммит с проверенным деревом. Отправка также нужна, если обновление основы создало коммит без новой разницы в индексе.
17. Если после синхронизации осталась содержательная разница активных страниц, создаёт новый реквест или обновляет единственный существующий.

## Сценарий 1. Ничего не изменилось

Условия:

- все активные страницы совпадают с JSON основной ветки;
- в служебной ветке нет старых ожидающих изменений;
- страницы не исчезали.

Результат:

- JSON не перезаписываются;
- индекс пуст;
- коммит и `push` не выполняются;
- новый реквест не создаётся;
- существующий реквест не закрывается автоматически, но результат запуска помечает его как потерявший актуальную разницу.

## Сценарий 2. Изменился цвет существующего токена

Экшен заново вычисляет весь активный объект токена, а не исправляет только `hex` или `rgba`. Поля получают фиксированный порядок:

```json
{
	"rgba": "rgba(239, 49, 36, 1)",
	"hex": "#ef3124",
	"figma": "accent_inverted/primary",
	"web": "--color-dark-accent-primary-inverted",
	"alias": "accentColorPrimaryInverted"
}
```

Если изменился только цвет, идентификаторы остаются вычисленными из тех же имён. JSON сравнивается с основной веткой, изменение попадает в отчёт как обновление активного токена.

## Сценарий 3. На активной странице появился новый токен

Новый фрейм или состояние проходит тот же путь, что существующие:

1. проверяется тип узла;
2. проверяется имя;
3. проверяется порядок состояний;
4. вычисляются JSON-ключ и Figma-путь;
5. проверяется, что заливка ровно одна, она видимая, сплошная и связана с переменной или цветовым стилем Figma;
6. вычисляются все пять полей;
7. ключ добавляется в отсортированную активную группу.

Ручного списка разрешённых токенов нет. Если имя подходит формуле текущего контракта, код менять не нужно.

## Сценарий 4. Токен исчез с активной страницы

Исчезновение токена не удаляет историю из JSON. Старый объект переносится из активной группы в отдельный хвост устаревших ключей и получает `deprecated: true` последним полем.

Активная и устаревшая группы сортируются отдельно. Поэтому устаревший ключ не остаётся на старом месте, а переносится в правильную часть файла. Описание реквеста перечисляет каждый ключ, впервые ставший устаревшим.

## Сценарий 5. Устаревший токен вернулся

Если ключ снова вычисляется из Figma:

- старый устаревший объект не используется частями;
- создаётся новый активный объект со всеми пятью полями;
- `deprecated` исчезает;
- ключ возвращается в отсортированную активную группу;
- отчёт помечает его как восстановленный.

## Сценарий 6. Появилась новая стандартная страница, JSON отсутствует

Пример страницы: `colors_new_palette.json`.

Экшен вычисляет:

- `id`: `new-palette`;
- цель: `styles/colors_new_palette.json`;
- исходную версию основной ветки: отсутствует, значит логически `{}`;
- права нового файла: `0644`.

После успешной проверки всех страниц новый файл создаётся атомарно. Если другой процесс успел создать его после чтения, экшен не перезаписывает чужой файл, а завершает запуск ошибкой гонки.

Все ключи нового файла считаются новыми относительно основной ветки. На повторном запуске до слияния отчёт остаётся рассчитанным относительно основной ветки, поэтому реквест не теряет описание только из-за того, что служебная ветка уже содержит готовый JSON.

## Сценарий 7. Появилась новая страница, а JSON уже существует

Наличие JSON не подключает набор, но после появления одноимённой страницы он становится исходной версией:

- найденные на странице ключи пересобираются как активные;
- старые ключи, которых нет на странице, становятся устаревшими;
- новые ключи добавляются;
- порядок всего файла нормализуется общим алгоритмом.

## Сценарий 8. Страница существует, но имеет особый модуль

При точном совпадении `pageName` явный модуль имеет приоритет. Автоматическая стандартная фабрика не создаёт второй набор.

Так сохраняются более строгие реальные контракты имён и состава состояний. Универсальные `empty`, общий порядок полей, проверка цветов, сортировка и обработка устаревших токенов всё равно выполняются ядром.

## Сценарий 9. Страница исчезла, JSON уже опубликован в основной ветке

Сам опубликованный JSON не удаляется. Он просто перестаёт участвовать в синхронизации.

Если для страницы существует явный модуль особых правил, её имя и целевой JSON попадают в отдельный список `inactiveConfiguredPages` и в журнал запуска. Это позволяет отличить намеренно отсутствующую стандартную страницу от пропущенной ранее настроенной особой страницы.

Если постоянная служебная ветка уже содержала ожидающее изменение этого JSON от прошлого запуска, экшен восстанавливает файл байт-в-байт из точного SHA основной ветки, фиксирует согласование отдельным коммитом и отправляет ветку обычным `push`. Результаты текущей синхронизации активных страниц этот шаг не отменяет.

Если ожидающей разницы не было, никаких файловых или сетевых изменений из-за этого JSON не происходит.

## Сценарий 10. Страница исчезла до слияния нового JSON

В основной ветке JSON отсутствует, а в служебной он был добавлен прошлым запуском. Экшен удаляет файл из служебной ветки и отправляет согласующий коммит. Это убирает незавершённое добавление, не затрагивая опубликованные данные.

## Сценарий 11. Страница отсутствует, но в `styles` лежит другой JSON

Экшен не сканирует `styles` как список заданий. Такой файл:

- не читается как палитра;
- не изменяется;
- не требует исключения;
- не попадает в реквест.

Он может начать синхронизироваться только после появления страницы с точным допустимым именем в единственном Color Exporter.

## Сценарий 12. Во фрейме есть `empty`

После общей проверки, что ребёнок фрейма является именованным `RECTANGLE`, экшен сразу пропускает узел с точным именем `empty`. Размер, координаты, заливки, обводки, привязки, позиция, количество и соседние состояния значения не имеют.

Например, все варианты ниже дают один и тот же экспортируемый `default`:

```text
[default]
[empty, default]
[default, empty]
[empty, default, empty]
```

Точно так же `empty` рядом с `hover` или `press` не создаёт, не заменяет и не помечает состояние. После удаления всех `empty` применяется обычный контракт набора: интерактивный фрейм может содержать допустимое непустое подмножество состояний, а набор только с `default` по-прежнему запрещает настоящий `hover` или `press`. Фрейм из одних `empty` запрещён.

## Сценарий 13. На странице ошибка структуры

Запуск останавливается, если найдено хотя бы одно из условий:

- повтор экспортной страницы;
- неверный тип узла;
- пустое имя;
- повтор секции, фрейма, состояния или вычисленного ключа;
- неизвестное или переставленное состояние;
- отсутствуют обязательные дети;
- цвет имеет не ровно одну заливку, включая случай с дополнительной скрытой заливкой;
- единственная заливка скрыта, не является `SOLID` или не связана с переменной либо цветовым стилем Figma;
- цветовой канал находится вне диапазона;
- имя не соответствует контракту.

Поскольку расчёт двухфазный, ошибка последней страницы не разрешает записать уже рассчитанные первые страницы.

## Сценарий 14. Локальный запуск одного набора

Параметр `--palette <id>` выбирает набор после обнаружения страниц. Это может быть особый модуль или новая стандартная страница: например, `--palette new-palette` выбирает `colors_new_palette.json`. Соседние JSON не читаются и не записываются. Неизвестный идентификатор считается ошибкой.

Параметр `--palette all` выбирает все обнаруженные наборы. Если экспортных страниц нет, результат пуст; наличие особых модулей для запуска не требуется. В режиме `--check` файлы не записываются; код завершения `2` означает найденную разницу.

## Сценарий 15. Единственный Color Exporter содержит много страниц

Полный REST-ответ `GET /v1/files/JGR9GpDXUneyYHfDdb7BDT` загружается один раз. Все страницы разбираются из одного ответа, поэтому наборы одного запуска видят один и тот же снимок. Другие Figma-файлы экшен не запрашивает.

## Сценарий 16. Временная ошибка Figma

Транспортная ошибка, `429` или временная серверная ошибка повторяются ограниченное число раз. `Retry-After` до 30 секунд соблюдается точно. Если сервер требует ждать дольше, запуск завершается с просьбой повторить его позже: запрос не отправляется раньше разрешённого времени. Один тайм-аут охватывает и получение ответа, и чтение JSON-тела.

Постоянные ошибки, неправильный JSON и ошибки контракта не повторяются. Токен передаётся только заголовком и удаляется из текста ошибок.

## Сценарий 17. Сбой записи или параллельное изменение

Перед заменой экшен повторно проверяет исходный текст и права каждого существующего файла. Новый путь обязан всё ещё отсутствовать.

Сначала полностью записываются новые тексты и исходные копии. После этого существующие цели заменяются атомарным переименованием, новые создаются атомарной жёсткой ссылкой без перезаписи. При перехваченной ошибке установленные версии восстанавливаются, только если не изменились после установки. Неудачное восстановление сохраняет исходную копию и сообщает её путь. Ограничения при аварийном завершении процесса и параллельной записи описаны в [`FILE_WRITES.md`](FILE_WRITES.md).

## Сценарий 18. Служебная ветка уже существует

Экшен не переписывает историю принудительно. Он получает удалённую ветку, открывает её локально и обычным `merge` добавляет текущую основу. Конфликт останавливает запуск и требует человека.

Обычный `push` также защищает от параллельного изменения удалённой ветки: если она ушла вперёд после чтения, отправка будет отклонена.

## Сценарий 19. Реквеста ещё нет

После успешного коммита и `push` экшен создаёт реквест в основную ветку. Описание на русском содержит:

- файлы и количества узлов;
- активные и устаревшие токены;
- новые, восстановленные и изменённые активные ключи;
- полный список ключей, впервые получивших `deprecated: true`;
- предупреждение, что автоматического слияния нет.

## Сценарий 20. Один реквест уже открыт

Новый реквест не создаётся. Экшен обновляет только заголовок и описание существующего реквеста после синхронизации ветки.

## Сценарий 21. Найдено два реквеста из служебной ветки

Ситуация неоднозначна. Экшен останавливается до коммита и `push`, чтобы не выбрать реквест догадкой.

## Сценарий 22. `push` успешен, а создание реквеста упало

Коммит остаётся в служебной ветке. На следующем запуске итоговый JSON уже находится в ветке, но отчёт снова рассчитывается относительно основной. Если ветка всё ещё отличается, экшен создаёт или обновляет реквест без лишнего коммита и без повторного `push`.

## Сценарий 23. Исчезновение страницы убрало последнюю разницу реквеста

Экшен отправляет согласующий коммит, чтобы убрать прежнюю ожидающую разницу исчезнувшей страницы. Новый реквест не создаётся. Уже открытый реквест не закрывается и не меняется через API; результат запуска возвращает признак `stalePullRequest`, а журнал сообщает номер реквеста и необходимость проверить его вручную.

## Сценарий 24. В служебной ветке найден посторонний файл

Сначала экшен отдельно разбирает отличающиеся пути вида `styles/colors_<имя>.json`. Если такой JSON больше не относится к активной странице, он считается ожидающим результатом исчезнувшей страницы и автоматически возвращается к основной ветке либо удаляется, если в основной ветке его ещё не было.

После этого экшен сравнивает итоговый индекс с точным SHA основной ветки. В оставшейся разнице разрешены только JSON активных страниц с допустимым типом и правами. Посторонний путь — например, `README`, исходник или настройка — останавливает запуск до коммита, отправки и вызова GitHub API. Пробелы в имени не отбрасываются. Незаписанное изменение рабочего файла не может скрыть посторонний файл в отправляемом дереве.

## Что всегда остаётся ручным

- создание и наполнение страниц Figma;
- проверка и принятие реквеста человеком;
- слияние реквеста;
- решение об удалении уже опубликованного JSON из основной ветки;
- описание особого контракта, если стандартные правила не подходят.
