# Архитектура

## Модель в одном абзаце

Инструмент состоит из конвейера, стандартной фабрики и сменных особых инструкций. Конвейер умеет получить файл, найти страницы, строго прочитать одинаковую геометрию, создать результат, отсортировать и безопасно записать его. Стандартная фабрика подключает новую страницу без исходного модуля. Особый модуль знает только отличия своего набора. Локальная команда и GitHub Actions запускают один конвейер, поэтому у них нет двух расходящихся реализаций экспорта.

## Направление зависимостей

```text
cli.mts ───────────────┐
                      ├── run-palettes.mts ── core/*
run-github-action.mts ─┘          ↑
                                  │ контракт функций
                            palettes/*.mts
```

Ядро не импортирует ни BlueTint, ни другой конкретный набор. Модули палитр могут импортировать общие формулы ядра и `_shared.mts`. Обратная зависимость запрещена.

## Поток данных

```text
discover-palettes.mts      обнаружение особых модулей страниц
    ↓
единственный Color Exporter через Figma REST или сохранённый полный ответ
    ↓
parse-layout.mts          список страниц и проверка CANVAS → SECTION → FRAME → RECTANGLE
    ↓
_create-standard.mts      правила новой стандартной страницы в памяти
или особый модуль         key, figma, web, alias
    ↓
format-color.mts          rgba, hex
    ↓
token-contract.mts       точные пять полей
    ↓
sync-palette.mts         активная группа + устаревший хвост + список изменений
    ↓
stable-order.mts         единый независимый от локали порядок
    ↓
json-files.mts           чтение, сериализация и проверка реального пути
    ↓
file-transaction.mts     подготовка, замена и восстановление при сбое
    ↓
git-operations.mts       исходная основа + проверка итогового индекса
    ↓
report-contract.mts      проверка и сортировка машинного отчёта
    ↓
pull-request-body.mts    стабильное русское описание реквеста
    ↓
publication-plan.mts     проверенное решение о коммите, отправке и реквесте
```

## Ответственность файлов

### `core/types.mts`

Содержит общие структуры данных: минимальный узел Figma, контракт палитры, активный токен, счётчики, результат синхронизации и узкий интерфейс сетевого ответа. Внешние данные всё равно проверяются во время выполнения; типы не заменяют эти проверки.

### `core/assertions.mts`

Содержит общий способ остановить запуск с понятной причиной, проверку обычного JSON-объекта и точного порядка полей.

### `core/token-contract.mts`

Хранит единственный список публичных полей активного токена:

```text
rgba, hex, figma, web, alias
```

Парсер проверяет не только наличие, но и порядок, строковый тип, непустое значение и совпадение `figma` с вычисленным идентификатором.

### `core/stable-order.mts`

Проверяет JSON-ключи и сортирует их по явному алфавиту. Здесь нет системной локали и настроек отдельных палитр. В этом же файле находится простое сравнение технических имён модулей по кодовым единицам.

### `core/discover-palettes.mts`

Автоматически находит файлы особых наборов и проверяет:

- имя файла совпадает с `id`;
- `id`, целевой JSON и Figma-страница уникальны;
- путь относительный, нормализованный и не выходит из репозитория;
- имя страницы совпадает с именем JSON;
- `default` объявлен среди состояний;
- все обязательные функции существуют;
- дополнительных полей нет, поэтому модуль не может указать другой файл или переопределить `empty`.

Это не реестр всех наборов. Служебные файлы начинаются с `_` и не участвуют в обнаружении. Новые стандартные наборы появляются из страниц Figma во время запуска.

### `core/fetch-figma.mts`

Выполняет ограниченный по времени REST-запрос к постоянному адресу единственного Color Exporter. Один таймер охватывает заголовки и тело. Перенаправления запрещены, незавершённое тело ошибочного ответа отменяется. Временные ошибки повторяются; `Retry-After` до 30 секунд соблюдается точно, более длительный интервал останавливает запуск без преждевременного повтора. Секрет не помещается в адрес или сообщение об ошибке.

### `core/figma-source.mts`

Хранит единственный разрешённый ключ `JGR9GpDXUneyYHfDdb7BDT` и собранный из него REST-адрес. Модули палитр источник не задают.

### `core/parse-layout.mts`

Знает допустимый шаблон имени экспортной страницы и общую геометрию. Возвращает стабильный список страниц, умеет отличить отсутствующую настроенную страницу от дубля. Здесь же находится безусловное игнорирование прямоугольника с точным именем `empty`: его остальные свойства не читаются. Модуль палитры не получает этот узел и не может изменить правило. Имена секций и состав настоящих состояний делегируются стандартным или особым правилам. Повторы узлов, неверные типы, состояния не по порядку и дубли вычисленных ключей считаются ошибкой.

### `core/token-sources.mts`

Хранит соответствие вычисленных имён исходным состояниям одной страницы. Ключи и `web` проверяются на уникальность во всей палитре; `figma` и `alias` — внутри явно переданного модулем режима. Сообщает оба источника совпадения, не сравнивает значения цветов и не читает старый JSON. Отдельный экземпляр создаётся на палитру, поэтому одинаковые имена разных наборов друг другу не мешают.

Режим передаётся в `PaletteIdentity.mode` вместе с `key` и `figma`. Это внутренние данные проверки: объект JSON по-прежнему содержит только пять полей. Разбор режима остаётся в правилах палитры; ядро не разбирает префиксы JSON-ключей и не содержит исключений по названиям наборов.

### `core/format-color.mts`

Требует ровно одну заливку всего: видимую, `SOLID` и связанную с переменной или цветовым стилем Figma. Ручная заливка и любая дополнительная, включая скрытую, запрещены. После проверки связи модуль переводит числовое значение REST в `rgba` и `hex`; все каналы и коэффициенты прозрачности проверяются на диапазон от 0 до 1.

### `core/sync-palette.mts`

Полностью заменяет каждый активный объект новым каноническим объектом. Исчезнувшие ключи сохраняет в отдельном хвосте с `deprecated: true`. Одновременно возвращает машинные списки новых, восстановленных, изменённых и впервые устаревших ключей.

### `core/json-files.mts`

Отвечает только за файлы:

- не разрешает целевому пути выйти из корня репозитория;
- читает исходный текст и права;
- допускает отсутствие нового целевого JSON;
- сериализует JSON единым способом;
- проверяет реальные папки и конечный файл, не допуская символических ссылок.

### `core/file-transaction.mts`

Принимает уже рассчитанные тексты. Разделяет подготовку всех новых и исходных копий, последовательную установку, восстановление и очистку. Перед заменой сверяет исходное состояние; перед восстановлением — принадлежность установленной версии. Не скрывает ошибки очистки и оставляет исходную копию при неудачном восстановлении. Узкий интерфейс файловых операций нужен для воспроизводимых испытаний отказов. Точные гарантии и ограничения — в [`FILE_WRITES.md`](FILE_WRITES.md).

### `core/run-palettes.mts`

Организует двухфазный запуск. Загружает единственный Color Exporter один раз, объединяет найденные страницы с особыми модулями и создаёт стандартные определения для остальных страниц. Явный модуль имеет приоритет при точном совпадении страницы. Отсутствующая страница пропускается и не читает JSON. Сначала все активные палитры вычисляются; только после общего успеха результаты передаются записи.

Модуль различает:

- `changed` — желаемый JSON отличается от исходной версии основной ветки;
- `writeNeeded` — желаемый JSON отличается от текущего файла рабочей ветки.

Второе поле остаётся внутренним. Разделение нужно для восстановления реквеста после прошлого успешного `push`.

Исходный JSON можно передать картой или ленивой функцией. Ленивый вариант позволяет GitHub Actions корректно обслуживать новый целевой путь, который стал известен только после чтения Figma.

### `palettes/_shared.mts`

Содержит только доказанные общие формулы:

- режим переменной `light/` или `dark/` остаётся в JSON-ключе, но удаляется из Figma-пути;
- режим токена `static_` остаётся и в ключе, и в Figma-пути;
- режим переменной и режим токена взаимоисключающие;
- внутренние `/`, `_` и `-` пути сохраняются в `figma`, а `/` и `-` превращаются в подчёркивания только в ключе;
- `web` строится из полного ключа;
- `alias` строится из Figma-пути;
- токен создаётся в каноническом порядке.

Здесь же `definePalette` создаёт неизменяемую копию настроек. После импорта модуль не может случайно поменять страницу или порядок состояний.

Файл не содержит условий по `id`.

### `palettes/_create-default-only.mts`

Это фабрика для наборов, где после игнорирования любых `empty` единственным настоящим состоянием остаётся `default`. Она создаёт стандартную обвязку, но получает правила секции и фрейма из отдельного файла набора. По умолчанию действуют формы `light/<путь>`, `dark/<путь>` и `static_<путь>`. Поэтому похожие модули короткие, а особенности всё равно остаются видимыми при ревью.

BlueTint, Decorative и Promo не используют эту фабрику: у них есть состояния взаимодействия, поэтому их состав фрейма описан явно.

### `palettes/_create-standard.mts`

Создаёт полное `PaletteDefinition` для страницы, которой нет среди явных модулей. Из имени страницы стабильно выводит `id` и `targetJson`, использует общий контракт секций, фреймов и настоящих состояний. Универсальный `empty` уже обработан ядром до вызова фабричных правил. Фабрика ничего не записывает в `src/palettes`: определение существует только внутри текущего запуска.

### `action/git-operations.mts`

Изолирует команды Git. Отличает отсутствие удалённой ветки от сетевой ошибки, продолжает историю существующей ветки, читает JSON из точного SHA. Возвращает ожидающие изменения исчезнувших страниц к основной ветке. Проверяет точные имена, типы и права файлов итогового индекса, включая его полную разницу с основной веткой. Сохраняет идентификатор проверенного дерева и сверяет его с коммитом перед отправкой.

### `action/publication-plan.mts`

Чистая функция без файловых и сетевых действий. Сопоставляет результат синхронизации с разницей каждого файла, проверяет список открытых реквестов и готовит описание. Возвращает готовое решение: нужен ли коммит, нужна ли отправка, какой реквест создать или обновить. Смысловые ошибки обнаруживаются до публикации, а не после неё.

### `action/types.mts`

Описывает только тот маленький срез GitHub и `@actions/exec`, который действительно использует инструмент. Это не связывает ядро с реализацией GitHub Actions.

### `action/report-contract.mts`

Принимает только структурированный результат конвейера. Проверяет согласованность счётчиков со списками, запрещает дубли и сортирует файлы и ключи.

### `action/russian-forms.mts`

Выбирает правильную русскую форму для чисел 1, 2, 5, 11 и их продолжений. Описание реквеста не содержит ручных фраз для конкретного числа.

### `action/pull-request-body.mts`

Строит маркдаун из уже проверенных данных: таблицу, итоги, списки новых устаревших ключей и гарантии. В нём нет анализа текста или ИИ.

### `action/run-github-action.mts`

Связывает готовые части: проверяет окружение и основную ветку, готовит служебную ветку, передаёт стандартную фабрику и ленивое чтение основы, запускает синхронизацию, сообщает о настроенных особых страницах без источника Figma, согласует остаток ветки с исчезнувшими страницами, проверяет индекс и всё дерево, при необходимости создаёт коммит и `push`, а затем создаёт или восстанавливает один реквест.

### `tools/fixture-layout.mts`

Удаляет из REST-ответа идентификаторы и метаданные, оставляя только структуру и цвет. Также умеет построить нормализованную раскладку из активных JSON для первоначального учебного слепка.

### `tools/update-full-fixture.mts`

Собирает десять ожидаемых JSON и обезличенный Figma-файл в самодостаточную папку. После записи запускает реальный конвейер в режиме проверки и отклоняет слепок, который не воспроизводит ожидаемый текст.

## Почему стандартная фабрика не превращается в общий «супермодуль»

Стандартная фабрика описывает один открытый контракт: `light/<путь>` или `dark/<путь>` для режима переменной, `static_<путь>` для режима токена, простые имена фреймов и непустое подмножество `default`, `hover`, `press`. Любое число `empty` ядро уже безусловно отбросило. Отличия отдельных наборов нельзя прятать в фабрику условными ветками. Это граница декомпозиции: повторяется механизм — выносится; отличается смысл набора — остаётся в его модуле.

## Как выглядит результат одного набора

`runPalettes` возвращает объект без секретов и абсолютных путей:

```js
{
    paletteId: 'bluetint',
    targetJson: 'styles/colors_bluetint.json',
    changed: false, // разница с выбранной исходной версией, а не факт записи
    changes: {
        newTokenKeys: [],
        restoredTokenKeys: [],
        changedActiveTokenKeys: [],
        newlyDeprecatedTokenKeys: [],
    },
    summary: {
        sections: 0,
        frames: 0,
        rectangles: 0,
        placeholders: 0,
        tokens: 0,
        oldTokens: 0,
        resultTokens: 0,
        activeTokens: 0,
        deprecatedTokens: 0,
        newTokens: 0,
        restoredTokens: 0,
        changedActiveTokens: 0,
        newlyDeprecatedTokens: 0,
    },
}
```

Этот объект одновременно служит выводом локальной команды и единственным источником описания реквеста.

## Три уровня проверок

1. Маленькие модульные сценарии проверяют отдельные формулы и ошибки.
2. `full-regression.test.mts` прогоняет десять палитр и побайтно сравнивает 2057 активных и 232 устаревших токена.
3. `git-integration.test.mts` создаёт временные настоящие Git-репозитории и проверяет восстановление после ошибки API, блокировку постороннего файла и реальное согласование исчезнувшей страницы.

Временные репозитории удаляются после каждого сценария. GitHub API в этих проверках заменён локальной заглушкой, поэтому реквесты не создаются.

## Граница отчуждаемости

Стандартный набор подключается новой страницей `colors_<название_набора>.json` в единственном Color Exporter. Исходник, реестр и пустой JSON заранее не нужны. Даже каталог особых модулей может быть пустым.

Особый набор получает отдельный `*.mts`, проверки, инструкцию и данные полного сценария. Ядро и GitHub-обвязка не получают условий по имени набора.

Отсутствие страницы означает отсутствие синхронизации. Ожидающая разница служебной ветки автоматически возвращается к основной, но опубликованный JSON не удаляется из основной ветки. Удаление производственного файла остаётся отдельным разрушительным решением.
