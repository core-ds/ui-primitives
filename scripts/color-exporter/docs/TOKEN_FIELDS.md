# Как экшен строит поля токена

Этот документ описывает стандартный алгоритм, общий для всех наборов. Инструкция конкретной палитры либо прямо подтверждает этот алгоритм без изменений, либо перечисляет только свои отличия. Никаких полей из старого активного объекта экшен не копирует: каждый найденный в Figma токен создаётся заново.

## Входные данные одного состояния

Для расчёта используются только проверенные машинные данные раскладки:

- имя секции, например `dark/accent_inverted`;
- имя фрейма, например `primary`;
- имя настоящего состояния: `default`, `hover` или `press`;
- числовой цвет единственной заливки из ответа Figma REST;
- метаданные REST, подтверждающие, что заливка связана с переменной или цветовым стилем Figma.

Служебные прямоугольники `empty` до этого шага уже отброшены. Они не соответствуют состояниям и не участвуют ни в одной формуле.

## 1. JSON-ключ

Стандартная секция имеет один из трёх видов:

```text
light/<путь>
dark/<путь>
static_<путь>
```

`light` и `dark` — режимы переменной Figma. Они отделяются от пути первым `/`. `static` — режим токена: он записан в имени переменной, отделяется `_` и остаётся частью пути.

| Имя секции | Как трактуется | Основа ключа | Основа `figma` |
|---|---|---|---|
| `light/accent` | режим переменной `light`, путь `accent` | `light_accent` | `accent` |
| `dark/qualitative-duocolor/set-c` | режим переменной `dark`, путь `qualitative-duocolor/set-c` | `dark_qualitative_duocolor_set_c` | `qualitative-duocolor/set-c` |
| `static_accent` | режим токена `static`, записанный в имени переменной | `static_accent` | `static_accent` |

Алгоритм:

1. Проверить имя секции правилом конкретного набора.
2. Разобрать `light/` или `dark/` как режим переменной либо сохранить `static_` как начало имени переменной.
3. Если путь секции заканчивается на `_inverted`, временно удалить этот суффикс из пути для ключа и запомнить признак инверсии.
4. В оставшемся полном пути секции заменить `/` и `-` на `_`.
5. В имени фрейма заменить `-` на `_`.
6. Соединить нормализованный путь секции и фрейм через `_`.
7. Если был признак инверсии, добавить `_inverted` после имени фрейма.
8. Для `default` ничего больше не добавлять. Для другого состояния добавить `_<state>`.

Формула:

```text
key = normalize(sectionWithoutInverted)
    + "_"
    + normalize(frame)
    + (inverted ? "_inverted" : "")
    + (state === "default" ? "" : "_" + state)
```

Пример:

```text
dark/accent_inverted + primary + hover
→ dark_accent_primary_inverted_hover
```

Готовый ключ обязан состоять только из `a-z`, `0-9` и `_`. Два состояния не могут дать одинаковый ключ. Ключи, которые JavaScript считает целочисленными индексами, запрещены: это строки от `"0"` до `"4294967294"` без ведущих нулей. Такие свойства автоматически перемещаются перед остальными и нарушают порядок токенов. Ограничение относится и к историческим JSON. Строки `"00"`, `"01"` и `"4294967295"` индексами не являются и остаются допустимыми.

## 2. Поле `figma`

Алгоритм использует путь из имени секции без перекодирования:

1. Для `light/<путь>` и `dark/<путь>` удалить режим переменной вместе с первым `/`.
2. Для `static_<путь>` сохранить имя секции целиком.
3. Сохранить внутренние `/`, `_`, `-` и конечный `_inverted` ровно как в пути.
4. Добавить исходное имя фрейма через `/`; дефисы в нём сохраняются.
5. Для `default` закончить путь. Для другого состояния добавить `/<state>`.

Стандартная формула:

```text
figma = (section начинается с light/ или dark/
         ? часть section после первого "/"
         : section)
      + "/"
      + frame
      + (state === "default" ? "" : "/" + state)
```

Пример:

```text
dark/accent_inverted + primary + hover
→ accent_inverted/primary/hover
```

Пример режима токена:

```text
static_accent + primary
→ static_accent/primary
```

Это вычисляемый стабильный путь из проверенного имени секции, а не копия произвольного отображаемого имени узла. Никакого обратного кодирования `_set-c` в `/set-c` нет.

## 3. Поля `rgba` и `hex`

Настоящий цветовой прямоугольник обязан иметь ровно одну заливку всего:

- заливка видима;
- тип равен `SOLID`;
- нет второй заливки, в том числе скрытой;
- заливка связана с переменной или цветовым стилем Figma;
- ручной цвет без такой связи запрещён.

REST возвращает вместе с привязкой уже вычисленные числовые каналы цвета. Экшен использует эти числа как значение цвета, но не считает само наличие чисел доказательством привязки.

Расчёт:

```text
R = round(color.r × 255)
G = round(color.g × 255)
B = round(color.b × 255)
alpha = roundToTwoDigits(color.a × fill.opacity × rectangle.opacity)
```

Отсутствующие коэффициенты прозрачности равны `1`. Каждый исходный канал и коэффициент обязан находиться в диапазоне от `0` до `1`.

Поле `rgba`:

```text
rgba(R, G, B, alpha)
```

Поле `hex` всегда записывается строчными буквами:

- при `alpha = 1`: `#rrggbb`;
- при `alpha < 1`: `#aarrggbb`, где `aa = round(alpha × 255)`.

Для `rgba(239, 49, 36, 1)` результат равен `#ef3124`.

## 4. Поле `web`

Поле строится только из готового JSON-ключа:

1. заменить каждый `_` на `-`;
2. добавить префикс `--color-`.

```text
dark_accent_primary_inverted
→ --color-dark-accent-primary-inverted
```

## 5. Поле `alias`

Поле строится из готового пути `figma` и известного состояния:

Состояние передаётся явно и обязательно. Оно не определяется по последнему слову пути: фреймы с именами `hover` и `press` могут содержать собственное состояние `default`.

1. Для `hover` или `press` убрать последний сегмент состояния из пути и запомнить его. Для `default` путь не сокращать.
2. Отделить последний оставшийся сегмент как имя токена.
3. В семейных сегментах убрать `_inverted` и запомнить признак инверсии.
4. Разбить части по `-` и `_`.
5. Первую часть семейства записать в `camelCase`, последующие части — в `PascalCase`.
6. Добавить слово `Color`.
7. Добавить имя токена в `PascalCase`.
8. При инверсии добавить `Inverted`.
9. Для состояния не `default` добавить его в `PascalCase`.

```text
accent_inverted/primary/hover
→ accentColorPrimaryInvertedHover
```

Слово `Color` всегда стоит непосредственно перед именем токена, даже если семейство состоит из нескольких сегментов.

## 6. Порядок полей активного объекта

Экшен создаёт ровно пять полей и всегда в одном порядке:

```json
{
	"rgba": "rgba(239, 49, 36, 1)",
	"hex": "#ef3124",
	"figma": "accent_inverted/primary",
	"web": "--color-dark-accent-primary-inverted",
	"alias": "accentColorPrimaryInverted"
}
```

Порядок равен:

```text
rgba → hex → figma → web → alias
```

Он одинаков для нового, изменённого и восстановленного из устаревших токена.

## 7. Если токен исчез или вернулся

Если старого активного ключа нет среди рассчитанных из Figma, его исторический объект сохраняется, прежнее поле `deprecated` удаляется из старой позиции и `deprecated: true` добавляется последним полем.

Если уже устаревший ключ снова рассчитан из Figma, старый объект целиком отбрасывается. Экшен заново создаёт стандартные пять полей, а `deprecated` исчезает.

## 8. Порядок токенов в файле

Активные и устаревшие ключи сортируются отдельно по полному JSON-ключу, затем соединяются:

```text
sort(active) + sort(deprecated)
```

Используется зафиксированный алфавит `_0123456789abcdefghijklmnopqrstuvwxyz`, а не настройки языка операционной системы. Исключений для отдельных наборов нет.

## 9. Проверка двух источников одного имени

Проверяются уже вычисленные имена, а не сходство исходных названий или цветов:

- ключ JSON и `web` уникальны в пределах палитры;
- `figma` и `alias` уникальны внутри режима палитры;
- одинаковый `alias` у версий `light` и `dark` допустим;
- совпадение `rgba` или `hex` у разных токенов допустимо.

Режим передаётся из правил палитры в служебном поле `PaletteIdentity.mode`. В JSON это поле не попадает. Проверяются только настоящие состояния текущей страницы Figma, независимо от наличия файла в коде. `empty` и старые устаревшие объекты в этой проверке не участвуют.

Например, фреймы `x1` и `x-1` одного семейства в одном режиме дают разные ключи, но один `alias`. Экспорт останавливается до записи любого рассчитанного JSON и указывает оба исходных пути и ключа. Последний встретившийся токен никогда не перезаписывает первый молча.

## 10. Допустимые отличия набора

Особый модуль может менять только явно документированные части:

- допустимые имена секций и фреймов;
- перечень настоящих состояний;
- формулу идентификатора или объекта токена, если стандарт действительно неприменим.

Требования к заливке, порядок пяти полей, обработка `empty`, разделение активных и устаревших ключей и стабильная сортировка остаются общими.
