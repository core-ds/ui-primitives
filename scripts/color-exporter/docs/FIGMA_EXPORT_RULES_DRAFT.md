# Как синхронизируются цвета

Экшен читает страницы `colors_<название_набора>.json` и синхронизирует одноимённые файлы в `styles`.
Если страница есть, а файла ещё нет — файл создаётся автоматически.
Если страницы для JSON из репозитория нет — он не синхронизируется.

При ручном запуске экшен получает один снимок файла Color Exporter через Figma REST. Сначала определяет страницы для экспорта, затем ищет соответствующие JSON в коде. Другие Figma-файлы не читает.

> Страница с этой инструкцией называется `.gitignore` и не участвует в синхронизации.

## 1. Что экшен читает в раскладке

```text
Страница CANVAS → имя файла JSON
└── Секция SECTION → режим и семейство
    └── Фрейм FRAME → имя токена
        └── Прямоугольник RECTANGLE → состояние и цвет
```

Экшен принимает только эту вложенность. Другие типы узлов и дополнительные уровни на экспортной странице считаются ошибкой.

Имя настоящего прямоугольника задаёт состояние. Допустимы `default` (обычное), `hover` (наведение), `press` (нажатие), именно в таком порядке. Любые состояния можно пропускать.

Прямоугольники с точным именем `empty` — заглушки. Экшен полностью игнорирует их, включая заливки, и не определяет, какое состояние они заменяют. Если не учитывать заглушки, во фрейме должно остаться хотя бы одно настоящее состояние.

## 2. Откуда берутся имена и цвет

Имена в JSON вычисляются из имён секции, фрейма и состояния. Цвет берётся из числовых значений заливки прямоугольника в ответе Figma REST.

У настоящего цветового прямоугольника должна быть ровно одна заливка: видимая, типа `SOLID`, связанная с цветовой переменной или цветовым стилем Figma. Ручной цвет без привязки и дополнительные заливки, даже скрытые, запрещены.

Экшен проверяет наличие привязки, но не сверяет имя привязанной переменной или стиля и фактически применённый режим с именами в раскладке.

## 3. Пример готовой записи

Секция `dark/accent_inverted`, фрейм `primary`, состояние `hover`. Для примера цвет заливки — `rgba(239, 49, 36, 1)`.

```json
{
    "dark_accent_primary_inverted_hover": {
        "rgba": "rgba(239, 49, 36, 1)",
        "hex": "#ef3124",
        "figma": "accent_inverted/primary/hover",
        "web": "--color-dark-accent-primary-inverted-hover",
        "alias": "accentColorPrimaryInvertedHover"
    }
}
```

Один настоящий прямоугольник — одна запись. Все пять полей рассчитываются заново и всегда идут в порядке `rgba → hex → figma → web → alias`.

## 4. Режим и ключ JSON

В секциях `light/<семейство>` и `dark/<семейство>` первая часть обозначает режим переменной Figma. Она входит в ключ и `web`, но не в `figma` и `alias`.

В секции `static_<семейство>` режим токена `static` записан в имени самой переменной. Он остаётся во всех именах с учётом формата каждого поля. Экшен определяет это по имени секции, а не по настройкам переменной.

```text
Ключ JSON = <секция без конечного _inverted> + "_" + <фрейм>
            + <суффикс инверсии> + <суффикс состояния>
```

В секции и фрейме `/` и `-` заменяются на `_`.
Если секция заканчивалась на `_inverted`, этот суффикс добавляется после имени фрейма. Иначе суффикс инверсии пустой.
Для `default` суффикс состояния пустой; для `hover` — `_hover`, для `press` — `_press`.

```text
Без инверсии:
dark/accent + primary + hover
→ dark_accent + _ + primary + _hover
→ dark_accent_primary_hover

С инверсией:
dark/accent_inverted + primary + hover
→ dark_accent + _ + primary + _inverted + _hover
→ dark_accent_primary_inverted_hover
```

## 5. Поля figma и web

`figma` — путь токена.
Взять имя секции и убрать начальное `light/` или `dark/`, если оно есть. Остальное сохранить, включая `static_`, внутренние разделители и `_inverted`. Добавить имя фрейма через `/`; для состояния, отличного от `default`, добавить ещё `/hover` или `/press`.

```text
dark/accent_inverted + primary + hover
→ accent_inverted/primary/hover

static_accent + primary + default
→ static_accent/primary
```

`web` — имя CSS-переменной.
В готовом ключе JSON заменить каждый `_` на `-` и добавить в начало `--color-`.

```text
dark_accent_primary_inverted_hover
→ --color-dark-accent-primary-inverted-hover
```

## 6. Поле alias

`alias` — вычисленное имя токена для кода. Оно строится из пути `figma` и состояния, взятого из имени прямоугольника.

```text
<семейство> + Color + <имя токена> + <Inverted> + <состояние>
```

1. Для `hover` и `press` убрать из пути конечный сегмент состояния. Для `default` путь не сокращать.
2. Последний оставшийся сегмент — имя токена, предшествующие — семейство. В каждом сегменте семейства проверить конечный `_inverted`. Удалить найденный суффикс и запомнить инверсию; если он встречается более чем в одном сегменте, это ошибка.
3. Разбить семейство и имя токена на части по `/`, `_` и `-`. Соединить без разделителей: первая часть семейства со строчной буквы, остальные части и имя токена — с заглавной. Цифры сохраняются.
4. Поставить `Color` перед именем токена. При инверсии добавить `Inverted`, затем `Hover` или `Press` для соответствующего состояния. Для `default` окончание состояния не добавлять.

```text
accent_inverted/primary/hover + состояние hover
→ accent + Color + Primary + Inverted + Hover
→ accentColorPrimaryInvertedHover
```

## 7. Поля rgba и hex

Числа из Figma REST переводятся в формат проекта: каналы RGB — целые числа от 0 до 255, прозрачность — от 0 до 1 с округлением до двух знаков. Итоговая прозрачность учитывает цвет, заливку и сам прямоугольник.

`rgba` записывается как `rgba(R, G, B, alpha)`.

`hex` записывается строчными буквами: `#rrggbb` для непрозрачного цвета, `#aarrggbb` для полупрозрачного. В последнем случае байт прозрачности `aa` стоит в начале и равен округлённому `alpha × 255` в шестнадцатеричной записи.

> Точные формулы — в [TOKEN_FIELDS.md](TOKEN_FIELDS.md).

## 8. Что меняется при повторном запуске

Каждый запуск сравнивает текущую Figma с версией основной ветки, зафиксированной для этого запуска, а не с результатом прошлого экспорта.

Если страница есть:
• Токен найден в Figma → его пять полей рассчитываются заново.
• Токен есть в основной ветке, но исчез из Figma → его значения сохраняются, последним полем добавляется `deprecated: true` — пометка устаревшего токена.
• Уже устаревший токен по-прежнему отсутствует → его объект сохраняется без изменений.
• Устаревший токен вернулся → запись рассчитывается заново, пометка `deprecated` исчезает.

Сначала идут активные токены, затем устаревшие. Каждый блок отдельно сортируется по полному ключу с фиксированным порядком символов `_0123456789abcdefghijklmnopqrstuvwxyz`. Правило общее для всех наборов.

Пока запрос на слияние открыт:
Повторный запуск обновляет его по текущей Figma и основной ветке. Поэтому новый токен, добавленный и убранный до слияния, исчезает из изменений без `deprecated`: в основной ветке его ещё нет.

Если страница исчезла:
Незавершённые изменения её JSON убираются из запроса на слияние. Файл, существующий в основной ветке, сохраняется в её версии. Новый файл, существовавший только в этом запросе, убирается целиком.

После слияния или закрытия:
После слияния принятые изменения становятся частью основной ветки и не показываются повторно. Если запрос закрыли без слияния, следующий запуск снова рассчитывает изменения относительно основной ветки.

## 9. Когда экспорт останавливается

Ошибка любой экспортной страницы останавливает весь экспорт до записи рассчитанных JSON и отправки изменений. Экшен сообщает причину; раскладку и имена автоматически не исправляет.

Если после преобразования два источника в Figma получают одно имя в коде, экспорт останавливается и показывает оба места: страницу, секцию, фрейм, состояние и идентификатор узла, если он есть в ответе Figma.

> Ключ JSON и `web` должны быть уникальны в наборе; `figma` и `alias` — внутри режима этого набора. Поэтому одинаковый `alias` у светлой и тёмной версии допустим. Одинаковые значения цвета у разных токенов тоже допустимы.

Конфликт со служебной веткой, посторонние изменения в ней или несколько открытых запросов из неё также останавливают отправку. Экшен не перезаписывает ветку принудительно и не выполняет слияние автоматически.
