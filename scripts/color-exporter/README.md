# Синхронизация цветовых токенов

Экшен для `core-ds/ui-primitives` читает экспортные страницы через Figma REST, детерминированно пересобирает цветовые JSON и готовит запрос на слияние для проверки. Новая стандартная страница автоматически становится новым набором и при необходимости создаёт одноимённый JSON.

Процесс [«экспорт цветов»](../../.github/workflows/export-colors.yml) запускается только вручную из основной ветки репозитория. Он не меняет Figma и не выполняет слияние. Локальная команда рассчитывает JSON без отправки в GitHub; параметр `--check` также запрещает запись файлов.

## Что уже готово

- десять проверенных особых палитр: BlueTint, Brand, Decorative, Go, Monochrome, Promo, Qualitative, Sequential, Students и X5;
- автоматическое подключение будущих стандартных страниц без исходного модуля;
- запуск без единого особого модуля и выбор нового стандартного набора через `--palette`;
- строгий TypeScript без отключения проверки типов;
- локальная команда синхронизации;
- процесс GitHub Actions с ручным запуском;
- самодостаточный обезличенный слепок 2057 активных и 232 устаревших токенов;
- модульные проверки, проверка полного слепка и проверки на временных Git-репозиториях;
- русское описание реквеста со списком впервые устаревших токенов;
- документация общей логики и отдельная инструкция для каждой палитры.

## Главная идея

Инструмент разделён на три части:

1. Общее ядро получает файл, проверяет раскладку, переводит цвет, объединяет результат со старым JSON, сортирует и безопасно записывает файлы.
2. Стандартная фабрика в памяти создаёт правила для новых страниц `colors_*.json`.
3. Модуль палитры хранит только осознанные отличия конкретного набора: более узкие имена, состав состояний или формулы путей.

Поэтому стандартная палитра подключается самим фактом наличия страницы в единственном Color Exporter. Отдельный файл в `src/palettes` нужен только для отклонения от общего контракта, а ядру не нужны условия вида `if (palette.id === ...)`. Полный порядок описан в [`docs/ADD_OR_REMOVE_PALETTE.md`](docs/ADD_OR_REMOVE_PALETTE.md).

## Гарантии результата

- ИИ и Figma MCP не участвуют в рабочем алгоритме.
- Рабочий источник — полный ответ Figma REST только для Color Exporter `JGR9GpDXUneyYHfDdb7BDT`.
- В имени секции `light` и `dark` отделяются `/` как режимы переменной Figma, а режим токена `static` записывается в имени переменной через `_` и сохраняется в пути.
- Активный токен всегда пересоздаётся с полями `rgba`, `hex`, `figma`, `web`, `alias` именно в этом порядке.
- Новый токен проходит тот же путь, что существующий; ручного списка токенов нет.
- Два источника одного вычисленного имени останавливают экспорт с указанием обоих путей. Ключ и `web` уникальны в палитре, `figma` и `alias` — внутри режима; одинаковые цвета и ожидаемые совпадения между `light` и `dark` допустимы.
- Любое число прямоугольников с точным именем `empty` в любой позиции безусловно игнорируется; их остальные свойства не читаются, а сами узлы не сопоставляются с состояниями.
- Настоящее состояние обязано иметь ровно одну видимую `SOLID`-заливку, связанную с переменной или цветовым стилем Figma; ручные и дополнительные скрытые заливки запрещены.
- Активные ключи сортируются по зафиксированному алфавиту, независимо от языка операционной системы.
- Исчезнувший токен не удаляется: он переносится в отдельный отсортированный хвост и получает `deprecated: true` последним полем.
- Уже устаревший исторический объект сохраняет внутренний порядок полей.
- Сначала вычисляются все палитры. Запись начинается только после успеха каждой из них.
- Единственный Color Exporter загружается один раз за запуск; других источников экшен не знает.
- Тайм-аут охватывает и получение ответа, и чтение JSON-тела. Временные ошибки повторяются ограниченно; `Retry-After` учитывается.
- Источник списка наборов — страницы `colors_<название_набора>.json`; JSON без страницы не требует исключения и не синхронизируется. Отсутствие всех экспортных страниц также допустимо.
- Новая стандартная страница создаёт `styles/<имя страницы>` атомарно с правами `0644`, даже если файла раньше не было.
- Исчезнувшая страница перестаёт синхронизироваться. Если от прошлого запуска в служебной ветке осталась ожидающая разница её JSON, экшен согласует этот путь с основной веткой; текущую синхронизацию активных страниц это не отменяет.
- Настроенные особые страницы, которых нет в Figma, отдельно перечисляются в журнале и результате запуска.
- До коммита проверяются точные пути, типы и права файлов итогового индекса, вся его разница с основной веткой и соответствие отчёту. Перед отправкой проверяется, что коммит содержит именно проверенное дерево.
- Принудительная отправка ветки и автоматическое слияние не выполняются.
- Повторный запуск после успешного `push`, но неуспешного вызова GitHub API, создаёт или обновляет реквест без лишнего коммита.

Списка исключений нет. Пока одноимённой страницы нет, любой JSON в `styles` остаётся вне синхронизации без специальной настройки.

Запись и восстановление при перехваченных ошибках описаны в [`docs/FILE_WRITES.md`](docs/FILE_WRITES.md). Это не общая транзакция файловой системы: процесс нужно запускать в отдельной рабочей папке без параллельного редактирования. При неудачном восстановлении сохраняются исходные копии и сообщаются их пути.

## Структура

```text
scripts/color-exporter/
├── docs/                                 подробные русские инструкции
│   └── palettes/                         отдельный файл на каждый набор
├── src/
│   ├── action/                           Git, GitHub и описание реквеста
│   ├── core/                             общее ядро
│   ├── palettes/                         подключаемые правила наборов
│   └── cli.mts                           локальная команда
├── tests/
│   ├── fixtures/full/                    полный обезличенный слепок
│   └── *.test.mts                        исполняемые сценарии поведения
├── tools/
│   ├── fixture-layout.mts                обезличивание и построение слепка
│   └── update-full-fixture.mts           проверка и обновление слепка
└── README.md
```

Процесс находится в `.github/workflows/export-colors.yml` в корне репозитория. Сборка использует корневые `package.json`, `package-lock.json` и `tsconfig.json`, без отдельного набора зависимостей. Файлы `.mts` компилируются в `.mjs`; GitHub Actions запускает код из `dist/color-exporter`.

## Быстрый старт

Нужен Node.js 24. Все команды ниже выполняются из корня `ui-primitives`, а не из папки экспортёра. Установите зависимости разработки по закреплённому `package-lock.json`:

```bash
npm ci
```

Проверить типы и все сценарии:

```bash
npm run typecheck
npm run test:colors
```

Проверить только рабочий код экшена с обязательными порогами 100% строк, 95% ветвей и 98% функций:

```bash
npm run test:colors:coverage
```

Запустить все найденные страницы через Figma REST:

```bash
npm run sync:colors -- --repo-root "/путь/к/ui-primitives"
```

Для этого в окружении должен быть `FIGMA_TOKEN`. Значение нельзя помещать в команду, `.env.example`, исходники, слепки, вывод или описание реквеста.

Запустить на сохранённом полном ответе REST:

```bash
npm run sync:colors -- \
  --repo-root "/путь/к/ui-primitives" \
  --figma-json "/путь/к/figma-response.json"
```

Проверить один набор без записи:

```bash
npm run sync:colors -- \
  --repo-root "/путь/к/ui-primitives" \
  --palette bluetint \
  --figma-json "/путь/к/figma-response.json" \
  --check
```

Код завершения `0` означает отсутствие изменений, `2` — найденную разницу в режиме `--check`, `1` — ошибку данных, настроек или доступа.

## Полный регрессионный слепок

Папка `tests/fixtures/full` полностью самодостаточна:

- `figma-sanitized.json` содержит только нужные страницы, секции, фреймы, состояния и цвета;
- `repository/styles` содержит десять ожидаемых JSON;
- `manifest.json` хранит стабильные количества и источник слепка.

В слепке нет идентификаторов узлов, пользователей, истории файла, ссылок, токена или другого закрытого содержимого.

Обычное обновление выполняется из живого REST:

```bash
npm run colors:fixture:update -- \
  --repo-root "/путь/к/ui-primitives" \
  --source live
```

Также поддержан локальный полный REST-ответ:

```bash
npm run colors:fixture:update -- \
  --repo-root "/путь/к/ui-primitives" \
  --source snapshot \
  --figma-json "/путь/к/figma-response.json"
```

Режим `normalized-json` нужен только для первоначального создания учебного слепка. Он строит раскладку из активных ожидаемых токенов и не заменяет живую проверку Figma.

## Что происходит с новым токеном

Прямоугольник `default` во фрейме `primary` секции `dark/accent_inverted` с цветом `rgba(239, 49, 36, 1)` даст:

```json
{
    "rgba": "rgba(239, 49, 36, 1)",
    "hex": "#ef3124",
    "figma": "accent_inverted/primary",
    "web": "--color-dark-accent-primary-inverted",
    "alias": "accentColorPrimaryInverted"
}
```

Если имя не соответствует документированному контракту, запуск остановится до записи. Алгоритм не угадывает неизвестные правила.

## Подключение к репозиторию

| Часть | Путь в `ui-primitives` |
|---|---|
| `src/` | `scripts/color-exporter/src/` |
| `tests/` | `scripts/color-exporter/tests/` |
| `tools/` | `scripts/color-exporter/tools/` |
| `docs/` | `scripts/color-exporter/docs/` |
| `README.md` | `scripts/color-exporter/README.md` |
| `.github/workflows/export-colors.yml` | `.github/workflows/export-colors.yml` |

Команды экспортёра добавлены в корневой `package.json`; зависимости типографики и других инструментов не менялись. Процесс выполняет `npm ci` и `npm run build`, затем запускает собранные проверки и только после их успеха читает Figma. Обычный `npm test` по-прежнему проверяет существующие утилиты SVG; проверки цветов вызываются отдельно через `npm run test:colors`.

Релизный скрипт учитывает только корневые `icons/`, `styles/` и `animations/`. Изменения вложенных тестовых JSON экспортёра не требуют выпуска пакета.
